# KORAS Product Profile

This repository is a **customer-facing, multi-tenant KORAS SaaS product**,
generated by `create-koras-app --profile product`. Confirm with
`.koras/project.yaml`; `project.profile` reads `product`.

Its users are customers and their end users. It is not the platform authority —
it consumes the KORAS Control Plane, it does not administer it.

## What this repository owns

| Domain | Meaning here |
|--------|--------------|
| Tenant isolation | Every row of customer data belongs to exactly one tenant |
| Organization context | The signed-in principal acts within one organization at a time |
| Customer onboarding | Sign-up, invitation, first-run, seat assignment |
| Tenant domains | Custom hostnames resolving to this product |
| Tenant branding | Per-tenant logo, palette, product naming |
| Subscriptions and plans | Read from the Control Plane; never authored here |
| Entitlements | Feature gates, decided by the Control Plane, enforced here |
| Customer-facing UX | Responsive, accessible, production-quality product surfaces |
| Tenant-aware storage | Object keys and access scoped by trusted tenant context |
| Observability | Logs, traces and metrics carrying tenant context, never secrets |

## Non-negotiable rules

1. **Never trust a tenant identifier supplied by a browser.** A tenant ID in a
   path, query string, body, header or cookie is a *request*, not *evidence*.
   Resolve the tenant from the verified session or a server-verified host
   mapping, then check that the requested tenant is one the principal may act
   for. Fail closed when the context is ambiguous.
2. **Never bypass authorization or RLS for convenience.** Not in a migration,
   not in a seed script, not behind a feature flag, not "temporarily" in a
   route handler. A service-role key must never reach a request path that a
   browser can reach, and never reach a client bundle at all.
3. **Authentication is not authorization.** A valid ZITADEL session proves who
   is calling. It says nothing about which tenant's data they may read or which
   operation they may perform. Check both, server-side, on every protected
   operation.
4. **Client-side guards are UX, not security.** Hiding a route, a button or a
   nav item changes what a user sees. It changes nothing about what the server
   will do when asked.
5. **Entitlements are enforced, not assumed.** A plan or feature flag read from
   the Control Plane is enforced on the server before the capability acts. A
   disabled control in the UI is the courtesy, not the boundary.
6. **Subscriptions and plans are Control Plane state.** Read them through
   `packages/api-client`. Do not create local plan tables, local pricing logic
   or a second billing lifecycle.

## Data and schema work

- Every tenant-owned table carries an explicit tenant column and an RLS policy
  that scopes on trusted context — not on a value the client can set.
- New tables default to RLS enabled and deny-by-default. Adding a table without
  a policy is an incomplete change, not a follow-up.
- Review cross-tenant leakage on every query, join, aggregate, cache key,
  background job payload and export.
- Reference `koras-supabase` and `koras-multitenancy` for the concrete
  patterns; this skill states the boundary, those state the mechanics.

## Frontend work

- Customer-facing means responsive and mobile-usable, not desktop-only with a
  breakpoint bolted on. Verify at a mobile width before declaring done.
- Target WCAG 2.2 AA. See `koras-accessibility`.
- Tenant branding is applied through design tokens, not by forking components
  per tenant.
- Cover loading, empty, success, error, unauthorized and forbidden states.
  "Forbidden" is a real state in a multi-tenant product, not an edge case.

## The authenticated product shell

Every signed-in page renders inside one shell, and its sidebar comes from one
registry. Both are inherited from the starter; neither is a component to fork.

- **Add a module, do not edit the shell.** A new area is an entry in
  `navigation` in `packages/branding/src/index.ts` — id, label, icon, href,
  group, order, and whatever gates it needs. Nothing in `packages/ui/src/shell`
  changes for a new page, and a change there is a change to every product.
- **Never branch on a role to choose a sidebar.** `resolveNavigation` takes the
  whole registry and the caller's access and returns what survives. A sidebar
  per role stops matching the server's rules the first time a role is added,
  and it fails in the direction that shows people things.
- **The registry is also the route gate.** `src/middleware.ts` looks the
  pathname up with `moduleForPath` and refuses with `canOpenModule` — the same
  function the sidebar uses. A module hidden for an authorization reason must
  therefore also be refused at its URL; if you find yourself wanting one without
  the other, the design has drifted.
- **Hiding is not authorization, still.** The middleware gate covers
  permissions, product access and the two role gates. It deliberately does not
  cover entitlements or tenant features, because those need a network read that
  must stay out of the edge runtime — a page performing a plan-gated operation
  checks the entitlement server-side itself.
- **Four gates, and they fail differently.** A missing capability or permission
  hides a module. A missing entitlement or feature hides it by default and can
  be shown locked, with an upgrade hint, when the product asks. An
  authorization failure is never locked: a locked entry advertises that an area
  exists.
- **Permissions are a closed set** in `packages/permissions/src/index.ts`, with
  the role-to-permission map beside them. Add both halves or the module is
  hidden from everybody and looks like a bug in the shell.
- **Product access is one function.** `productAccessFromOrganizationRoles` is
  the seam a per-product assignment store replaces. Do not scatter a second
  derivation beside it.
- **Team & Access is not the portal's Users page.** Organization membership,
  invitations, billing, subscriptions, domains and single sign-on belong to the
  KORAS Customer Portal. A product links out to it and reimplements none of it.

See `docs/PRODUCT_APP_SHELL.md` in the starter for the full standard.

## Testing

Alongside the common expectations in `koras-testing`, a product change is not
complete until cross-tenant access is tested negatively: a principal of tenant A
must be shown to be *unable* to read, write or enumerate tenant B's data through
the surface being changed.

## What does not belong here

Platform administration, provisioning, reconciliation, infrastructure registries
and `platform_admin` authorization live in the KORAS Control Plane. If a change
seems to need them, it is either a Control Plane change or a Control Plane API
call — not a new capability in this repository.
