# Postman standard

How every KORAS repository's Postman collection is produced, kept current,
and told apart from the tests a person adds by hand. This document explains
the generation architecture and the contribution rules only — it is not a
setup guide.

## Running the Collection

Import, environment, identity, token, and the first-run verification
sequence are step-by-step runbooks, kept separate because a LOCAL setup and
a DEV setup need different URLs, different identities, and different token
sources — combining them into one document is how a reader ends up pasting a
local token into a DEV environment.

- **LOCAL** (your own machine): `docs/api/postman-local-setup.md`
- **Deployed DEV**: `docs/api/postman-dev-setup.md`

## The one rule everything else follows

**A Postman collection is generated from the real, running API's own OpenAPI
schema. Nothing in a generated request is invented.**

Every KORAS Control Plane and product API is FastAPI. FastAPI computes an
OpenAPI 3.1 document from the routes, `Depends()` declarations, Pydantic
models and status codes that are actually registered — the same document it
would serve at its own /openapi.json route. `tooling/postman/scripts/extract_openapi.py`
gets that document by importing the service's own `app` object and calling
`app.openapi()` directly, without starting the process, opening a database
connection, or making a network call. That is the entire inventory step: a
route this script did not find is a route that does not exist in code, and a
route in a doc that this script does not find is a documentation gap, not
something the generator papers over by adding it anyway.

## Pipeline

```
extract_openapi.py          services/api's own app.openapi()  ->  openapi.json
        │
        ▼
openapi-to-postman.mjs       openapi.json  ->  generated collection
        │                    (folders by tag, bearer auth, example bodies from
        │                     schemas, status-code + content-type + timing
        │                     tests from the operation's declared responses)
        ▼
merge-custom.mjs             generated collection + templates/<profile>-custom.json
        │                    -> the collection a repository commits
        ▼
generate-environment.mjs     final collection  ->  DEV environment
                             (every {{variable}} the collection references,
                              plus the fixed identity variables every KORAS
                              environment needs)
```

`tooling/postman/scripts/generate.mjs` runs all four steps. It is what
`pnpm postman:generate` calls.

## Generated vs. custom

Two kinds of content live in the same collection file, and they are never
merged into one blob a human has to untangle:

- **Generated** — every folder built from a real tag in the OpenAPI schema:
  the request, its parameters, its example body, and a test script that
  asserts the operation's own declared status codes, content type and
  response time. Regenerating replaces this half entirely. Do not hand-edit
  it; the edit is silently lost on the next run.
- **Custom** — `tooling/postman/templates/<profile>-custom.postman_collection.json`,
  merged in by `merge-custom.mjs` and marked with a `koras.custom` note in
  each folder's description. This is where **CI Smoke** and
  **Security & Negative Tests** live, because both need a human to decide
  what "safe" and "the actual security contract" mean — a generator cannot
  derive either from a schema. Edit the template, not the generated file; the
  next `postman:generate` run re-reads it fresh.

## Why some things the brief for this standard asked for are deliberately absent

- **No `X-Tenant-Slug` / `X-Organization-Id` headers.** Read
  `services/api/koras_api/core/tenant.py` (product) or the Control Plane's own
  `organization_auth.py` before assuming otherwise: the
  tenant/organization comes from the verified token's claims, never from a
  request header or a path parameter the caller supplies. A collection that
  added such a header would be testing a security control the API does not
  have and would never notice if someone added one.
- **No `X-Request-Id` on product requests.** Control Plane accepts and echoes
  it (`X-Request-Id` is in its CORS `allow_headers`); no product template
  does. The generated test only asserts the header on the Control Plane
  collection, via `--correlation-header`.
- **No invented response schemas.** The example body for every request comes
  from the operation's own request-body schema in the OpenAPI document —
  concrete field names, not a guess at what a "reasonable" payload looks
  like.

## Regenerating a collection

From the repository root (Control Plane, or any product generated by this
starter):

```bash
pnpm postman:generate
```

If Python dependencies are managed by `uv` rather than a plain `python` on
`PATH` (true of every repository this starter generates today), pass the
interpreter explicitly:

```bash
pnpm postman:generate -- --python "uv run --no-project python"
```

This writes:

```
postman/<Name>-DEV.postman_collection.json
postman/environments/DEV.postman_environment.json
```

## Extending the custom fragment

To add a security test or a CI-safe smoke request, edit
`tooling/postman/templates/product-custom.postman_collection.json` (or the
`control-plane-` one) directly — it is an ordinary Postman collection
fragment, just `{"item": [...] }`. Ground every assertion in code: name the
file and function it comes from in the request's `description`, the way the
existing ones do. A security test that does not cite where the behavior it
asserts is implemented is exactly the kind of invented contract this standard
exists to avoid.

## What this does not (yet) do

- **No OpenAPI contract file is committed anywhere.** `extract_openapi.py`'s
  output is a build artifact consumed by the converter and discarded; nothing
  publishes it as `openapi.json` for a consumer to read independently, and
  no CI step validates a committed spec against the live routes because none
  is committed. A repository that wants OpenAPI as its own contract — for a
  client SDK, or for a non-Postman consumer — can run
  `python tooling/postman/scripts/extract_openapi.py --service-dir services/api --out openapi.json`
  directly; nothing here stops it, this standard just does not adopt it as a
  checked-in artifact yet. See "Next steps" below.
- **No Newman/CI wiring.** The `CI Smoke` folder is structured to be safe for
  unattended execution (nothing in it mutates state, and every request that
  needs a real token skips itself with `pm.test.skip` when `access_token` is
  unset rather than failing), but no workflow in `.github/workflows/` invokes
  it. Wiring it in is `tests/**` territory this pass did not touch.
- **Security & Negative Tests cover the boundary, not every route.** Missing
  auth, an invalid token, an inactive tenant, a conditional-write precondition
  and a malformed payload are each asserted once, against one representative
  endpoint, because the auth/tenant dependency they exercise is shared by
  every route that uses it — `AuthDep`, `TenantDep`, `PlatformReadDep` are
  applied the same way everywhere they appear. Extending coverage to a
  route-specific authorization rule (e.g., "only an `owner` may deactivate an
  account") needs a hand-written case per rule; none of those exist yet.

## Next steps (ranked)

1. **Commit the extracted OpenAPI document** alongside the collection (e.g.
   as `openapi.json` in the same `postman/` directory) and add a CI check
   that regenerating it produces no diff — the cheapest way to catch route
   drift between a merge and the
   next Postman regeneration, and the natural seed for a generated SDK later.
2. **Wire `CI Smoke` into `.github/workflows/` via Newman** on the same
   `develop`/`generator-integration` cadence the rest of the estate's gates
   run on, once a DEV server is reliably up for the job to hit.
3. **Extend Security & Negative Tests per authorization rule**, not just per
   dependency — starting with the routers that carry role checks beyond
   `AuthDep`/`TenantDep` (e.g. `accounts.py`'s role-gated transitions,
   `organizations.py`'s `requires()` calls).
