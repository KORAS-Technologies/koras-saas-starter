## YES.

- **Element:** the shell's root `<div className="flex min-h-screen flex-col bg-surface-muted">` at **`packages/ui/src/shell/product-shell.tsx.hbs:166-167`**.

Using it would force a prop down from the layout, i.e. an `apps/` edit. The shell root div is inside the provider and is the correct containment point.

**Minimum edit set:** two files, both under `packages/ui/`:
1. `packages/ui/src/shell/product-shell.tsx.hbs` — read the setting, emit `data-contrast` on line 167's div.
2. `packages/ui/src/styles/tokens.css` — add the `[data-contrast="high"]` override block.

**Mode consequence:** because the change is fully containable within `packages/ui` and touches no boundary, no floor signal fires (see §5) — so the execution mode is **not FULL**.

## 4. CHANGE CLASSES (`gate-invalidation.yaml`) — and the glob-anchoring finding

Mapping the expected edits to the classes at `gate-invalidation.yaml:29-101`:

| Edit | Intended class | Class glob (as written) | Matches the FACTORY path? |
|---|---|---|---|
| `profiles/product/template/packages/ui/src/shell/product-shell.tsx.hbs` | `frontend_code` (`:97-99`, `packages/**`) | `packages/**` | **NO** |
| `profiles/product/template/packages/ui/src/styles/tokens.css` | `frontend_code` | `packages/**` (also no `*.css` glob exists anywhere) | **NO** |
| `generators/create-koras-app/tests/product-shell.test.ts` | `automated_test_node` (`:59-64`, `**/*.test.ts`) | `**/*.test.ts` | **YES** |

**Finding (do not paper over):** the change-class path globs are written **relative to a generated product root** (`packages/**`, `apps/**`, `docs/**` — unanchored). In the factory the same production code lives at `profiles/product/template/packages/**`, which `packages/**` does **not** match (it is not `**/packages/**`). Consequences:

- The **production-code edits** (`.tsx.hbs`, `.css`) classify as **no change class** against the factory tree as written. `frontend_code` — the class that would invalidate `accessibility_pass`, `e2e_pass`, `screenshot_evidence_complete`, `independent_code_review` (`gate-invalidation.yaml:255-269`) — does **not** fire.
- The **test edit** *does* classify (`automated_test_node`, because it is anchored with `**/`). 
- `tokens.css` is a `.css` file: **no change class in the file matches any `.css` path** at all, factory or product. Even in a generated product it would only be caught by `frontend_code`'s `packages/**`; there is no CSS-specific class.

Net: as written, an impact classifier run against the factory would see this feature as **"a Node test changed"** and nothing else — inverting the real picture (production UI changed, tests followed). This is an asymmetry the gate-invalidation globs cannot express for factory-resident code, and it is a defect in the config's applicability to this repository, not something to route around. Recommend the factory either anchor these globs (`**/packages/**`, add a `**/*.css` → `frontend_code` entry) or document that gate-invalidation is evaluated post-generation only.

## 7. STYLING MECHANISM (`packages/ui/src/styles/tokens.css`)

Light/dark is handled by **one mechanism, not a class swap**:

1. `:root { color-scheme: light dark; }` (`tokens.css:34`) declares the document supports both appearances.
2. Every surface token is a **`light-dark(…, …)` pair** (`tokens.css:49-54`), so the browser resolves the appropriate half from `color-scheme`.
3. The Tailwind theme is declared **`@theme inline`** (`tokens.css:73-92`), so utilities compile to `var(--brand-*)` references rather than baked values — which is what lets a runtime override re-skin everything.
4. The switch is **`color-scheme` on `<html>`, and nothing else**: `ThemeToggle`/`THEME_SCRIPT` set `document.documentElement.style.colorScheme` (`theme-toggle.tsx.hbs:48,54`). No class, no palette swap.
5. Per-tenant brand overrides the same custom properties on a nested element (`brandStyle()` → `BrandScope` div, `brand-style.ts.hbs:20-53`, `brand-scope.tsx.hbs:47`); because each override is itself a `light-dark()` pair, the subtree keeps both appearances.

**Therefore high-contrast must follow the same token-override discipline, not invent a second one:** under a `[data-contrast="high"]` scope, **re-declare the same `--brand-*` custom properties** (foreground, background, surface, border, muted-foreground — and optionally a stronger `--brand-primary`/focus outline) as `light-dark()` pairs. Because Tailwind resolves through `var(--brand-*)` (`tokens.css:73-92`), this re-skins the whole subtree — including within `BrandScope` and across both appearances — with zero component changes, exactly as brand and theme already do. Do **not** add a parallel class-based palette or hardcoded colours (a component writing `bg-blue-600` "cannot be re-branded" — `tokens.css:16-18`); that would be the "second mechanism" the file's design forbids.

## 8. BLAST RADIUS / REVERSIBILITY

The blast radius is confined to the signed-in area and is small. The `data-contrast` marker sits on the shell's own root `<div>` (`product-shell.tsx.hbs:167`), so the CSS override in `tokens.css` is scoped to authenticated pages under the shell; public/marketing pages, which never render the shell, are visually unaffected even though they import the same stylesheet. There is no server, database, contract, migration, permission or tenancy surface in the change — one boolean read from an already-loaded context plus static CSS re-declaring existing tokens — so nothing outside `packages/ui` can regress and no data can be corrupted. Reversibility is trivial and total: the setting defaults to `False` (`standard.py:517`), so the feature is dark until a user opts in; disabling it is either clearing the setting (no marker emitted) or reverting the two `packages/ui` files, with no data to unwind and no migration to reverse. The only realistic failure mode is a *visual* one — a token pair with poor contrast, or a component that hardcoded a colour and so ignores the override — which is caught by the accessibility/screenshot gates rather than by anything structural, and is itself reversible by editing the single override block.
