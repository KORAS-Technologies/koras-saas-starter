# G7R2-F01 — manual test guide

Written by `test-documentation` before execution. `manual-qa` executes it and records
results in `manual-test-results.md`; the two are separate files so that the plan cannot
be quietly rewritten to match what happened.

## Why a person is required

`documentation-policy.yaml` `manual_qa.required_when`: the change alters something a
person sees, and its correctness depends on what the browser actually does. The
`not_required_when` exemption — *automated verification observes exactly what a person
would* — does not hold here. The automated assertions prove a rule was written into a
template and that an attribute appears in the DOM. Neither can see whether the page
became readable, and "the tokens resolved" is not the same claim as "a human can read
it".

## Environment

| | |
|---|---|
| Build under test | a product generated by `create-koras-app` from the commit under test |
| Application | the generated product's `apps/web`, signed-in area |
| Harness | the product template's Playwright harness with `E2E_DATABASE_URL` set, so the API and a real Postgres are running and a preference can actually be stored and read back |
| Account | the seeded member, from `e2e/support/seed.sql` |
| Widths | 1440 and 375 |

The exact commit, template digest, ports and account are recorded per case in the
results document. A result with no build context is not evidence.

## Cases

Every case records: ID, objective, priority, preconditions, test data, numbered steps
with action and expected, the actual result, a verdict of PASS, FAIL or BLOCKED, the
evidence reference, and — where it is not obvious — what each capture proves.

### G7R2-F01-TC01 — The flip

| | |
|---|---|
| **Objective** | With the preference on, the signed-in shell renders in the high-contrast palette; with it off, the page is exactly as it was and carries no marker. |
| **Priority** | Critical |
| **Preconditions** | Signed in as the seeded member. `accessibility.highContrast` unset, so the platform default false applies. Light appearance. |
| **Test data** | `accessibility.highContrast`: false, then true, then false |

1. Go to `/dashboard`. **Expected:** the shell renders in the stock palette.
   *Capture: the starting state. The later image is meaningless without it.*
2. Inspect the shell root element. **Expected:** no `data-contrast` attribute present.
3. Go to `/dashboard/preferences` and turn **High contrast** on. **Expected:** the
   control accepts the change and the value is saved.
4. Navigate back to `/dashboard`. **Expected:** the whole signed-in surface — page
   canvas, header, sidebar, cards — renders in the high-contrast palette. Not a patch
   of the page: all of it.
   *Capture: the transition this case exists to demonstrate.*
5. Inspect the shell root again. **Expected:** `data-contrast="high"`.
6. Turn the preference off and return to `/dashboard`. **Expected:** the page returns
   to the stock appearance and the attribute is absent again.
   *Capture: the return. A one-way change would pass step 4 and still be a defect.*

**Note on timing, recorded before execution rather than discovered during it.** The
effective settings are resolved once per request, on the server, in the dashboard
layout. The flip is therefore expected on the next server render — a navigation or a
reload — not necessarily the instant the toggle moves. If it appears instantly, record
that; if it needs a navigation, record that too. Either is a fact about the settings
framework, not about this change, and the results document says which was observed.

### G7R2-F01-TC02 — Structure survives when tint stops carrying it

| | |
|---|---|
| **Objective** | With surfaces no longer distinguished by tint, panels, cards and the sidebar remain distinguishable by their borders. |
| **Priority** | High |
| **Preconditions** | High contrast on; light appearance; 1440. |

1. Go to `/dashboard`. **Expected:** the sidebar is separated from the content by a
   clearly visible border, and any card reads as a bordered box rather than dissolving
   into the page.
   *Capture: proves the design's central trade — hierarchy moved from tint to border —
   actually works. A sentence cannot establish it.*

**This is the case most likely to fail**, and failing it is a real result: it would mean
the high-contrast palette is readable but unusable, and it would be a HIGH finding.

### G7R2-F01-TC03 — The dark appearance

| | |
|---|---|
| **Objective** | High contrast does not pin an appearance. In dark mode it is white on black, still maximal. |
| **Priority** | High |
| **Preconditions** | High contrast on. |

1. Switch the theme to dark. **Expected:** the shell is white text on black, not a
   light-mode page and not the stock dark palette.
   *Capture: proves the `light-dark()` pairs survived — the single most likely
   implementation slip is a flat hex, which would look correct in light and break here.*

### G7R2-F01-TC04 — A tenant brand does not defeat it

| | |
|---|---|
| **Objective** | The decisive case. An organisation's branding may not override a person's accessibility accommodation. |
| **Priority** | Critical |
| **Preconditions** | A tenant with a custom brand palette applied, so that the stock and branded appearances are obviously different. |

1. With high contrast **off**, load `/dashboard`. **Expected:** the tenant's brand
   colours are visible.
   *Capture: establishes that branding is actually in effect; without it, step 2 proves
   nothing.*
2. Turn high contrast **on** and reload. **Expected:** text, canvas and surfaces are the
   high-contrast palette, **not** the tenant's colours. The brand hue may still appear
   on the focus ring and primary actions, which are deliberately untouched.
   *Capture: proves precedence.*

**If the tenant's colours survive on text or background this is CRITICAL** and blocks
the feature. The cascade argument says it cannot happen; the argument is untested until
somebody looks.

### G7R2-F01-TC05 — 375px, keyboard and focus

| | |
|---|---|
| **Objective** | The mobile drawer and keyboard operation are unchanged, and focus stays visible against the high-contrast surfaces. |
| **Priority** | High |
| **Preconditions** | High contrast on; viewport 375 wide. |

1. Open the navigation drawer. **Expected:** the drawer panel renders in the
   high-contrast palette with a visible border, and the close control is reachable.
2. Tab through the drawer's controls. **Expected:** the focus ring is clearly visible
   against the new surfaces at every stop.
   *Capture: an accessibility condition that is visual — a focus ring that has become
   invisible against a changed background is exactly the regression this mode could
   introduce.*
3. Press Escape. **Expected:** the drawer closes and focus returns to the control that
   opened it, as it does today.

## What this guide does not cover, and where that is covered instead

- **Contrast ratios.** Measured by `accessibility-qa` against computed colours. A
  person looking at a screen cannot establish 4.5:1, and a screenshot cannot either.
- **`accessibility.fontScale` and `accessibility.reducedMotion`.** Still dead. Out of
  scope, recorded in the register row.
- **The OS forced-colors mode.** It outranks this preference by design and is not
  fought. Not a case here.
- **Persistence across sessions.** A property of the settings framework, proven by its
  own round-trip suite.

## Screenshot policy applied

Captures are taken at the points listed above and nowhere else: a starting state, each
transition the case exists to demonstrate, and the two visual accessibility conditions.
Navigation on the way to a screen is not captured. There is no maximum, and a case that
turns up something unexpected captures it with a written purpose.
